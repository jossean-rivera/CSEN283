# Before

- A **thread** is an execution context: it has its own registers and stack and is what the scheduler runs.
- A **process** is a resource container with an address space and resources such as global variables and open files. Its threads share those resources.
- Both processes and threads have states such as running and runnable. Strictly, the CPU executes a thread; it is also common to say that a process is running when one of its threads is running.

In xv6, each process has only one thread, so “process” and “thread” are often used interchangeably in this course.

## Kernel Image

The professor drew a long vertical rectangle representing physical memory. Looking at `kernel.ld`, the kernel image has the following sections:

| Starting address | Content in memory |
| --- | --- |
| `0x00000000` | |
| `0x80000000` | `entry.o` (from `entry.S`): sets up a stack and calls `start()`. |
| | `start.o` (from `start.c`), `proc.o`, `main.o`, and many other object files. |
| | `usertrap()`: dispatches user traps by checking `scause`; handles system calls, timer and device interrupts, and faults. |
| | `kerneltrap()`: dispatches traps that occur while already in kernel mode; handles timer and device interrupts and faults. |
| | `kernelvec`: kernel-trap entry point; saves registers and calls `kerneltrap()`. |
| | `trampoline.o`, which contains `trampoline`, `uservec`, and `userret`. `uservec` is the user-trap entry point: it saves registers in the trap frame, switches to the kernel page table, and enters `usertrap()`. `userret` switches back to the user page table, restores registers, and returns to user mode. |
| | `rodata`: read-only constant data. |
| | Initialized global variables (`data`). |
| | Uninitialized global variables (`bss`). |

*Types of traps include system calls, interrupts, and exceptions/faults.*

> [!info] Clarification: trampoline
> RISC-V does not automatically switch page tables on a trap. xv6 maps the trampoline page at the same high virtual address in both the user and kernel page tables, allowing `uservec` and `userret` to continue executing safely while switching page tables. The trap frame, one page below it, holds the saved user registers.

## Functions inside a system call

Professor: “You can call these functions in your program.”

This means a user program written in C can call system-call wrapper functions such as these. Each wrapper enters the kernel, which performs the requested operation.

- `getpid()` gets the calling process’s PID. It normally returns immediately and does not block or context-switch.
- `read()` may block when the requested data is not ready.
  - The calling process sleeps; the scheduler switches to another runnable process.
  - When the data becomes available, the process becomes runnable and eventually resumes `read()`.
- `exit()` terminates the process. xv6 marks it as a zombie and switches to the scheduler; its parent later reaps it with `wait()`.
- `sleep()` puts the process in the **sleeping** state and switches to the scheduler. When woken, it becomes runnable.

A process moves among states such as runnable, running, sleeping, and zombie.

## Kernel Logical Space

The kernel is loaded mostly contiguously, so its virtual layout is similar to its physical layout:

| Starting address | Content |
| --- | --- |
| `0x00000000` | |
| `0x80000000` | Direct mapping of the kernel and physical memory. |
| | Per-process kernel-stack area, with guard pages. |
| | Unused virtual-address space. |
| | Trampoline code, mapped to the trampoline’s physical page. |
| `MAXVA` | Maximum virtual address. |

- Executed in kernel mode.

# User Space

The logical user space is broken down as follows:

| Address | Content |
| --- | --- |
| `0x00000000` | Program text (code). |
| | Initialized data and `bss`. **BSS** (“Block Started by Symbol”) holds zero-initialized global and static variables; the loader initializes it to zero. |
| | User stack. |
| | Expandable heap. |
| | Trap frame, used by the trampoline to save user registers. |
| | Trampoline code, mapped at the same high virtual address as in kernel space. |
| `MAXVA` | |

- Executed in user mode.

**Note:** This is the overall structure of xv6.

# Process Creation

Discussing the slides the professor provided.

Each process has a **process ID** (`PID`), which is greater than 0. A PID may be reused after the previous process terminates.

`PID 0`: idle process, generated by the system.

`PID 1`: `init` process.

- Invoked by the kernel at the end of the boot procedure.
- In xv6, it must not exit; xv6 panics if it does.
- It is a normal user process, not a kernel process.
- On macOS, PID 1 is `launchd`. To see it, run `ps -p 1 -o pid,ppid,comm`.
- `init` adopts orphaned children so that every process has a parent.

Fun tip: run `ps -eo pid,ppid,user,comm | more`.

## Fork function

Call `fork()` to create a new process:

`Parent process` → `fork()` → `Child process`

- When a parent process calls `fork()`, it creates a child that is initially a copy of the parent.
- The child has a separate address space and a different PID.
- After the call, two processes execute in the system.
- Both resume at the statement immediately after `fork()`.
- `fork()` returns `0` in the child and the child’s PID in the parent. On failure, it returns a negative value in the parent.

Check the return value of `fork()`:

- `== 0`: running in the child process.
- `> 0`: running in the parent process.
- `< 0`: creation of the child process failed.

Example:

```c
void main(void)
{
    pid_t pid;
    pid = fork();
    if (pid == 0)
        ChildProcess();
    else
        ParentProcess();
}
```

### What happens when the parent terminates before the child?

In xv6, the kernel reparents each surviving child to `init` (PID 1). The child becomes an **orphan**, but it still has a parent that can eventually reap it.

The operating system releases most of the terminating parent’s resources, including its user memory, open files, and I/O buffers. Its process-table entry remains until its own parent reaps it.

### What happens when the child terminates before the parent?

If a child terminates before its parent and the parent has not collected its exit status, the child becomes a **zombie**. Most of the child’s resources are released, but its process-table entry, PID, and exit status remain so that the parent can collect them.

A parent reaps a zombie child by calling `wait()`. If the child has already exited, `wait()` returns immediately after collecting its status; otherwise, the parent waits until a child exits.

## Exec function

What if you want to create a child that is not a copy of the parent?

For example, when a shell runs `emacs`, it typically calls `fork()` and the child calls `exec()`. The child then runs Emacs instead of another copy of the shell.

`exec()` replaces the current process image with a new program. If it succeeds, the original program no longer exists, and execution never returns to the instruction after `exec()` in the old program.

```text
Parent process
   |
 fork()
   |
Child process
   |
 exec()
   |
Same process, new program
```

*`exec()` destroys the current program. If the parent calls `exec()` directly, the parent is replaced by the new program.*
